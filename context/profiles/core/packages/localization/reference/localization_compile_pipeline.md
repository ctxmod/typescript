# Localization Compile Pipeline

The two admissible localization implementation families — the compile-step family (typed per-locale output compiled from catalogs, a localization compiler settings file, single-source multi-target compilation, a staging-dir drift gate, compiler output inside the runtime package exposed as package exports, a CI compile leg) and the runtime-lookup family (catalogs read at a lookup API) — with an honest contrast and the generated/handwritten boundary between them.

Catalogs are the source of truth; something must turn them into what an
application renders. There are exactly two admissible implementation
families, and this profile mandates neither. The compile-step family
compiles catalogs into typed per-locale output before the application
runs; the runtime-lookup family loads catalogs and resolves identifiers
through a lookup API while the application runs. Both are legitimate
implementations of the same localization responsibilities, and the
choice between them is an application-profile decision recorded with the
application, not a law.

Two exemplars name the families. **Inlang/Paraglide** is the compile-step
exemplar: message sources are compiled by the Paraglide compiler into
per-message, tree-shakeable output, driven by an inlang project-settings
file. **An i18next-class library** is the runtime-lookup exemplar:
catalogs are registered as resources and resolved through the i18next
lookup surface at render time. Each is a concrete instance of its family,
named here so the families are recognizable — never a mandated choice.

## Family A: The Compile-Step Family

The compile-step family turns catalog files into generated code before
anything renders. One source set fans out to every platform target from
a single compilation.

**The localization compiler settings file.** The compile is driven by a
settings file — the inlang project settings in the exemplar — declaring
the compiler, the catalog path pattern, the supported locale set, and
where compiled output lands. It is the machine-readable binding between
the catalog tree and the compiler; it sits next to the catalogs it
configures and is reviewed with them. A change to it is a contract
change in effect, because it changes what every consumer receives. The
catalog tree's own declaration (authoring locale, supported set, path
pattern) is owned by the message-catalogs reference; the compiler
settings file is its compilation-side counterpart.

**Single-source multi-target compilation.** One catalog source set
produces every target:

- the web runtime target — compiled per-message modules the browser
  imports directly;
- native-platform string catalogs, generated directly for each platform
  that needs one.

Every target is generated from the same source in the same step, so no
two platforms render different words for the same identifier. The
compile step wraps the ecosystem compiler rather than reimplementing
message compilation — invoking the pinned compiler as a dependency of the
build, never transcribing its output format into hand-maintained code.

**A drift gate.** The compile family's currency check is a regenerate-
and-diff gate: regenerate every target into a temporary staging
directory, byte-compare against the committed tree, write nothing, and
exit non-zero with a per-file drifted list when they disagree. This is
the same gate shape the contract drift gate uses; the principle is owned
by the generated-code discipline reference and the mechanics by the
contract-drift-gates procedure
([Contract Drift Gates](../../contracts/reference/contract_drift_gates.md)).
Localization drift is rejected, never warned about: committed compiled
output must equal fresh compilation from the catalogs under the pinned
compiler.

**Compiler output inside the runtime package, exposed as package
exports.** The web compile target's output directory sits inside the
localization runtime package, and the package's exports map exposes it —
the message barrel under one export, per-message modules under a
wildcard — with the generated files declared side-effectful so bundlers
keep them. Consumers import messages as an ordinary package import, and
the generated functions tree-shake per message.

Generated-inside-the-package is the load-bearing choice, and it is
adoptable as the default posture: it makes compiled messages an ordinary
package export with ordinary module resolution, retiring any alias,
virtual-path, or bundler-plugin machinery a separate dist directory or a
virtual module would require. The output tree is generated and
regenerated by the compile step and never hand-edited, under the same
prohibitions as any other generated tree.

**A CI compile leg.** Where compiled output is untracked, every consuming
build runs the compile step first, and CI carries that step with a
comment explaining why: a fresh clone lacks the output, so the compile is
a prerequisite of the build, not an optimization. The leg follows the
same path-filtered discipline as the other pipeline legs — it triggers on
the surfaces whose change can affect what it verifies, which here means
the catalog tree, the settings files, and the runtime package.

## Family B: The Runtime-Lookup Family

The runtime-lookup family keeps catalogs as data and resolves them while
the application runs. Catalog resources are registered with a
localization library; view code asks for a message by identifier and
namespace; the library resolves the identifier against the active locale,
applies fallback, and formats interpolations.

The catalog authorship rules apply unchanged — the two-axis layout, the
entry shape, the completeness requirement, the single settings
declaration (message-catalogs reference). The families differ in what
consumes the catalogs, not in how catalogs are written.

What the family adds on the runtime side:

- **namespace-aware on-demand loading** — a namespace's catalog loads
  when the area that renders it loads, so the initial payload carries
  only the namespaces the first view needs;
- **a single lookup surface** — components never read catalog files and
  never re-declare message shapes; every render goes through the
  library's lookup;
- **server-side initialization** — the active locale and the loaded
  namespaces are established on the server before rendering, so a
  server-rendered view resolves the same message the hydrated client
  will resolve.

## The Honest Contrast

| Dimension | Compile-step | Runtime-lookup |
|---|---|---|
| Bundle payload | Per-message output tree-shakes with use; unused messages never ship | Namespaces ship whole; unused messages in a loaded namespace ship too |
| Type safety | Compile-time — a missing identifier or wrong-argument call fails the build | Structural — enforced by catalog typing and tests, not the build alone |
| Runtime cost | Near zero at render; resolution happened at compile | Lookup and formatting per render |
| Locale switching | Requires the switched-to locale's output present or fetched | Requires the locale's resources loaded; the library's dynamic loading handles it |
| Toolchain surface | A compiler, a settings file, a drift gate, a CI compile leg | A library, its initialization, and its loading configuration |
| Where a missing message appears | As a compile failure, before anything ships | At the lookup, in development and tests rather than in the build |

Neither column is superior; each is the right answer under different
conditions. The compile-step family's strengths are strongest where the
supported locale set is small and stable, where bundle payload matters,
and where a build-time guarantee that no message is missing is worth a
compile step. The runtime-lookup family's strengths are strongest where
locales are numerous or added often, where namespaces load on demand
across a large surface, and where a mature runtime library's loading,
fallback, and formatting behavior is worth its runtime cost.

The failure mode to avoid is not picking the wrong family — it is
half-picking both. Catalogs written for one family and consumed through
the other's machinery, or a compile step whose output is then read
through a runtime lookup layer, combine the costs of both and the
guarantees of neither.

## The Generated/Handwritten Boundary

The boundary between generated compiled output and handwritten source is
the boundary the rest of this profile draws, applied unchanged:

- **Catalog files are handwritten source** — authored, reviewed, and
  never regenerated.
- **Compiled per-locale output is generated** — reproducible,
  non-authoritative, subject to the two editing prohibitions, and
  drift-checked. The four properties and both prohibitions are owned by
  the generated-code discipline reference
  ([Generated-Code Discipline](../../contracts/reference/generated_code_discipline.md));
  this reference does not restate them.
- **Handwritten localization code is scoped to what the family does not
  generate**: locale resolution and negotiation, the runtime package's
  own source, preference and suggestion surfaces, and view composition
  that decides which message renders where. None of it restates a
  catalog entry, so none of it is contract duplication.

## Native Catalogs as Compile Targets

Where an application also ships to native platforms, the native string
catalogs are additional compile targets of the same pipeline, not a
separate translation effort. The same identifiers compile to each
platform's catalog format, and the outputs land in a dedicated
generated-output tree rather than inside an application. Generated
native bridge files carry a header naming their generator so no one
mistakes them for source, and they are excluded from the web tree's lint
discipline — generated output in another format, not web source that
happens to look odd.

A repository with no native surface simply has fewer compile targets.
The pipeline shape does not change: one source, as many targets as the
repository has platforms.
